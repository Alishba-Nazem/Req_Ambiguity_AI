# Backend API — Requirement Ambiguity AI

REST API for classifying a software requirement as **clean** or **ambiguous**, returning an ambiguity type, score, explanation, and suggested rewrite.

The two-stage BERT checkpoints in `ml/outputs_two_stage/` are used for inference only. This service does not train or modify the dataset.

## Setup

From the project root:

```text
python -m pip install -r ml/requirements.txt
python -m pip install -r backend/requirements.txt
copy .env.example .env
```

On macOS/Linux use `cp .env.example .env`. Set `LLM_API_KEY` only if you want LLM rewrites. The API starts without it.

Hugging Face **ZeroGPU Gradio** Space layout and env vars: [docs/huggingface-space.md](../docs/huggingface-space.md). Local development still uses this FastAPI app. The Gradio entry point is root `app.py` and does not replace these routes.

Weights must exist at:

- `ml/outputs_two_stage/stage_a/best_model/model.safetensors`
- `ml/outputs_two_stage/stage_b/best_model/model.safetensors`

## Run

```text
python -m uvicorn backend.main:app --host 0.0.0.0 --port 8000
```

Or:

```text
python -m backend.main
```

## GET `/api/health`

Liveness check. Always returns HTTP 200 if the process is up. Includes whether Stage A and Stage B are loaded. Does not expose paths, keys, or stack traces.

### Example

```text
curl http://localhost:8000/api/health
```

```json
{
  "status": "ok",
  "model_loaded": true,
  "stage_a_loaded": true,
  "stage_b_loaded": true,
  "error": null
}
```

If checkpoints are missing, `status` is still `"ok"` and `model_loaded` is `false`. `POST /api/analyze` then returns HTTP 503.

## POST `/api/analyze`

Classify one requirement with the two-stage model:

1. Stage A: clean vs ambiguous
2. Stage B: ambiguity type, only if Stage A predicts ambiguous
3. `ambiguity_score`: `round(P(ambiguous) * 100)` from Stage A (0–100, higher = more ambiguous)
4. `confidence`: probability of the **final** predicted label (Stage A if clean, Stage B type if ambiguous)
5. Template explanation (not generated by BERT)
6. Suggested rewrite (optional LLM, otherwise a local fallback)

### Request body

| Field | Type | Required | Rules |
| --- | --- | --- | --- |
| `requirement` | string | yes | Non-empty after trim; max 2000 characters |

```json
{
  "requirement": "The system should respond quickly."
}
```

### Success response (ambiguous)

HTTP 200

| Field | Type | Notes |
| --- | --- | --- |
| `requirement` | string | Trimmed input |
| `classification` | `"clean"` \| `"ambiguous"` | Stage A decision |
| `ambiguity_type` | `"lexical"` \| `"syntactic"` \| `"semantic"` \| `"syntax"` \| `"pragmatic"` \| `null` | Stage B; `null` when clean |
| `ambiguity_score` | integer 0–100 | From Stage A P(ambiguous), **not** the same as confidence |
| `confidence` | float 0–1 | Probability of the predicted class |
| `explanation` | string | Template based on type |
| `suggested_requirement` | string \| `null` | Present when ambiguous |

```json
{
  "requirement": "The system should respond quickly.",
  "classification": "ambiguous",
  "ambiguity_type": "pragmatic",
  "ambiguity_score": 78,
  "confidence": 0.81,
  "explanation": "This requirement depends on unstated context, assumptions, or expectations. The phrase 'quickly' is not defined with a measurable criterion.",
  "suggested_requirement": "The system shall respond to user requests within [specify maximum response time]."
}
```

### Success response (clean)

```json
{
  "requirement": "The system shall lock the account after 5 failed login attempts.",
  "classification": "clean",
  "ambiguity_type": null,
  "ambiguity_score": 8,
  "confidence": 0.94,
  "explanation": "The requirement is specific and measurable as written.",
  "suggested_requirement": null
}
```

### Example request

```text
curl -X POST http://localhost:8000/api/analyze ^
  -H "Content-Type: application/json" ^
  -d "{\"requirement\": \"The system should respond quickly.\"}"
```

macOS/Linux:

```text
curl -X POST http://localhost:8000/api/analyze \
  -H "Content-Type: application/json" \
  -d '{"requirement": "The system should respond quickly."}'
```

### Errors

All errors use:

```json
{
  "error": "human-readable message",
  "code": "validation_error"
}
```

| HTTP | `code` | When |
| --- | --- | --- |
| 422 | `validation_error` | Missing/empty/whitespace `requirement`, over 2000 characters, or invalid JSON |
| 503 | `model_unavailable` | Checkpoints missing, load failure, or inference failure |

Stack traces and API keys are never returned to the client.
